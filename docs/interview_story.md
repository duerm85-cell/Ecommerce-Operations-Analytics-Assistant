# 项目面试叙事

## 项目定位

Ecommerce Operations Analytics Assistant 是一个端到端电商运营数据分析平台。项目面向电商运营团队，将商品、用户、订单和广告数据组织成统一分析链路，通过 SQL、Python 和 Power BI 支持商品增长、客户价值、经营表现与广告投放效率分析。

项目重点不是单独展示某个图表或算法，而是还原企业数据分析工作的完整过程：从业务问题拆解、数据模型设计、ETL、指标口径治理，到多工具对账、数据质量验证和管理层决策看板交付。

## 项目背景

电商运营团队通常需要同时回答三类高频问题：

1. 哪些商品和品类值得继续投入，哪些商品需要优化或退出？
2. 哪些客户贡献了主要价值，哪些客户正在进入流失风险区间？
3. 每一元广告费带来了多少归因收入，预算应该向哪些渠道或活动倾斜？

这些问题横跨多个业务主题域。如果商品、用户、订单和广告数据各自独立，或者不同分析工具对同一指标使用不同口径，管理层看到的结果就可能互相矛盾。因此，本项目以统一模型和统一指标为基础，构建可复现、可验证、可解释的分析流程。

## 技术挑战

### 1. 如何设计业务数据模型

项目需要同时支持商品、客户、订单和广告分析。设计时围绕以下实体组织数据：

- `products`：商品属性、品类、价格、热度与机会评分所需字段。
- `users`：客户属性、地区、获客渠道及 RFM 分析所需标识。
- `orders`：订单金额、折扣、成本、状态、日期及商品与客户关联。
- `ads`：按日期和活动记录曝光、点击、花费、转化及归因收入。
- `calendar`：统一日期维度，为趋势、周期筛选和时间计算提供基础。

模型设计的关键不是增加表的数量，而是明确每张表的业务粒度、主外键关系、时间边界和过滤方向，使同一套数据能够稳定支持多个分析主题。

### 2. 如何统一指标口径

GMV、净销售额、毛利、复购率和 ROAS 等指标容易因订单状态、时间窗口或分母定义不同而产生偏差。本项目为每项核心指标明确：

- 业务定义；
- 计算公式；
- 纳入与排除规则；
- 时间窗口；
- 单位与空值处理方式。

例如，GMV 纳入完成和退款订单但排除取消订单；净销售额只统计完成订单；复购率使用 FY2025 固定窗口内完成订单不少于两笔的购买用户作为分子。详细口径见 [business_metrics.md](business_metrics.md)。

### 3. 如何保证 Python、SQL、DAX 一致

项目没有把任意一个分析工具视为唯一正确来源，而是将相同业务口径分别落实到 Python、SQL 和 DAX：

1. 先在指标字典中固定业务定义和过滤规则。
2. Python 负责可复现的数据处理、分析输出和基准结果计算。
3. SQL 负责数据库侧的主题分析，并通过本地可执行数据库验证结果。
4. DAX 负责 Power BI 筛选上下文下的指标计算与动态叙事。
5. 自动化检查比较关键 KPI，避免因实现语言不同产生口径漂移。

这种设计让指标能够被追溯：当看板数字出现异常时，可以沿着 DAX、SQL、Python 和源数据逐层定位，而不是只在可视化层面人工核对。

### 4. 如何构建可复现分析流程

真实分析项目必须能够重复执行并得到稳定结果。本项目通过以下方式保证可复现性：

- 使用固定随机种子和明确业务规则生成脱敏数据；
- 将数据生成、数据库构建、主题分析、看板资产生成、指标对账和测试组织为统一流程；
- 对数据规模、主外键、缺失值、数值范围、业务等式和日期边界进行自动检查；
- 将 Power BI 的 PBIP、PBIR 和 TMDL 源文件纳入版本控制；
- 记录运行方式、指标口径、验证结果和已知限制。

## 个人贡献

### 数据模型设计

- 设计商品、用户、订单、广告和日期主题域的数据结构。
- 明确数据粒度、实体关系、时间字段和分析边界。
- 兼顾 SQL 查询、Python 分析和 Power BI 建模的共同需求。

### 指标体系建设

- 建立 GMV、净销售额、毛利、毛利率、AOV、复购率、CTR、CVR、CPA、ROAS 等统一口径。
- 明确订单状态、时间窗口、分子分母和归因边界。
- 建立 Python、SQL、DAX 之间的指标对账机制，减少口径漂移。

### 数据分析流程设计

- 将数据生成、质量验证、加载、分析、结果导出和测试串联成可复现流程。
- 分别构建商品机会、经营表现、RFM 客户价值和广告效率分析。
- 为分析结论补充业务假设、建议动作和后续验证指标，避免只输出描述性图表。

### Power BI Dashboard 设计

- 设计经营总览、商品机会、用户价值和广告回报四个决策页面。
- 按照“一句话业务结论 → 核心 KPI → 原因证据 → 下一步行动”的顺序组织信息。
- 使用动态度量支持筛选上下文下的业务结论和行动建议。
- 统一导航、筛选器、金额单位、视觉规范和风险/机会表达。

## 面试回答：为什么不用真实交易数据？

### 推荐回答

真实订单、用户和广告数据包含客户隐私、交易信息、投放策略及企业经营结果，通常受到数据安全制度、保密协议和隐私法规约束，不适合直接放入公开代码仓库。为了同时保证合规性和项目可验证性，我采用固定随机种子与业务规则生成脱敏模拟数据，并保留真实企业分析中关键的数据关系、订单状态、指标口径和质量约束。

这个项目验证的是完整分析能力，而不是用公开仓库证明某家企业的真实经营表现。我重点展示了数据模型、ETL、指标治理、SQL/Python/DAX 对账、数据质量检查和 Power BI 决策交付。当获得企业授权的数据源后，可以替换采集和加载层，并沿用相同的数据模型、指标定义和验证框架；上线前再针对真实字段映射、权限、刷新频率和业务规则完成验收。

### 回答边界

- 不把模拟数据产生的经营结论包装成真实市场结论。
- 不声称广告归因收入等同于因果增量收入。
- 不使用未经授权的客户、订单或投放数据证明项目效果。
- 企业级能力体现在流程、治理、验证和可维护性，而不是数据必须来自某一家真实企业。

## 60 秒项目介绍

我搭建了一个端到端电商运营数据分析平台，面向商品增长、客户价值和广告投放效率三个核心业务问题。项目从商品、用户、订单、广告和日期模型开始，建立统一的 GMV、净销售额、毛利、复购率、AOV、CTR、CVR、CPA 和 ROAS 指标体系，再使用 Python、SQL 和 DAX 实现同口径计算与自动对账。分析结果最终进入四页 Power BI 决策看板，分别服务经营总览、商品机会、用户价值和广告回报分析。由于真实交易和客户数据属于企业敏感信息，公开版本使用固定种子和业务规则生成的脱敏模拟数据，但保留了完整的 ETL、质量验证和交付流程，因此能够清楚展示我从业务问题到数据产品落地的完整能力。
